I used to write periodic homelab update posts but they’d go stale almost immediately. So instead, I’m just going to keep this page current. It’s the state of things as of the last updated date at the bottom.

Everything is managed via a private Git repo with FluxCD handling the GitOps side of things.

The Hardware#

It’s a 4-node K3s cluster, all sitting under my desk. It was 5 until recently. A mix of whatever I’ve picked up cheaply over the years:

  • Control plane (chilli): An old ThinkPad X230 with an Intel i5 and 16GB RAM. This one got the biggest overhaul (more on that below). It’s now running Fedora CoreOS off a new 500GB SSD.
  • An x86 worker (bluey): 8GB RAM, 4 cores, running Debian 12. Its root disk is a 10GB flash drive, which has caused more trouble than I’d like to admit.
  • A Raspberry Pi 4 (raspberrypi): 4GB RAM, on Raspberry Pi OS (Debian 13 trixie). Needed cgroup_memory=1 cgroup_enable=memory added to /boot/firmware/cmdline.txt before k3s would run at all - undocumented anywhere obvious, but it turns out to be a pretty common requirement for k3s on newer Pi OS. It’s tainted arm=true:NoSchedule, so only stuff I’ve explicitly confirmed has arm64 images gets scheduled there. These days that’s mostly a spare CoreDNS replica.
  • The NAS itself (lucky): Ubuntu 24.04, running the ZFS array (two 12TB Seagate Ironwolf drives, mirrored). It’s tainted dedicated=jellyfin:NoSchedule so Jellyfin can transcode right next to the media. It’s also become the home for the cluster’s controllers (Flux, CloudNativePG, cert-manager, the Prometheus operator, Renovate) since it’s the only box with real cooling.

The fifth node, muffin (another X230), died. I re-pasted it alongside chilli and it never came back - it won’t boot on AC and dies about 2 seconds in on battery. So it’s been removed from the cluster and its workloads moved onto the others. Still more than enough compute for what I’m running, just with less slack than before.

What’s running#

The dashboard#

I use Homepage as a landing page. It shows all the services with live health checks and a cluster resource overview. It’s the first thing I check in the morning.

Media#

  • Jellyfin for video and audio streaming, with separate kids and adults profiles. The split is driven entirely by which folder something lives in
  • Navidrome for music (I use it with Subsonic clients on my phone), scrobbling to Koito for listening stats
  • Audiobookshelf for audiobooks and podcasts
  • Pinchflat for converting YouTube channels into podcast feeds. It replaced Podsync
  • Calibre-Web for ebooks
  • Picard for tagging and organising music metadata

Productivity#

  • Miniflux for RSS - it’s fast and stays out of the way
  • Paperless-ngx for scanning and archiving documents. The OCR is brilliant, I just scan everything and search for it later. Tika and Gotenberg are back on so it can ingest office documents too
  • AFFiNE as my workspace for notes, docs and whiteboards. Signups are locked and the AI features point at my own model endpoint
  • Journiv as a self-hosted journal. It replaced Memos
  • CryptPad for end-to-end encrypted documents, though it’s on its way out in favour of AFFiNE
  • Wallabag for saving articles to read later

Self-hosted infrastructure#

  • Gitea with Valkey for caching. This has gone from a side Git server to the main home for my code. I moved 88 repos over from GitHub and archived them there, and my container images moved from ghcr.io to Gitea’s registry. The homelab repo is the one exception. It stays on GitHub so Flux can still rebuild the cluster if Gitea itself is broken, which avoids the circular dependency I was worried about.
  • Immich with Redis. This is probably my favourite thing running on the cluster - it’s a full Google Photos replacement and it’s genuinely good
  • Coder for self-hosted cloud dev environments, with its own Postgres. I’ve got an always-on dev workspace running there now that I SSH into from wherever
  • speaches as a self-hosted Whisper server for speech-to-text

I’ve also been culling. Matrix went earlier in the year, and since then Minecraft, my IRC stack (soju, The Lounge and a Slack gateway), Speedtest Tracker, Filebrowser, Memos, Podsync and Perkeep have all been removed. Fewer apps means less to patch, less to back up and less attack surface. I’d rather have a smaller setup I actually use.

AI agents#

This replaced my old local-LLM setup entirely (previously llama.cpp in RPC mode, Open WebUI as the chat interface, and Planka wired up via a custom Python bridge). That stack was fun to build but experimental in the bad way - it fell over often and wasn’t something I actually relied on.

What’s there now is a small system I’ve built myself rather than deployed off the shelf - the images are all built on Gitea now:

  • Hermes - a voice/chat AI agent gateway, with its own dashboard. This is the actual front door I talk to.
  • Honcho - the agent memory/context service behind Hermes. It has its own Postgres plus its own API, deriver, and Redis components.
  • family-ops - home automation and family reminders glue, tied into Hermes. It’s picked up school alerts, email triage into the calendar and a daily booklet.
  • hamcp - an MCP bridge that exposes Home Assistant as tools the agent can call.
  • A personal CRM - Postgres with NocoDB on top and an MCP server Hermes can call. I send a voice note over Telegram, it gets transcribed by the Whisper server above, and Hermes files it against the right person.

The other one I’m pleased with is a self-heal job. Every 6 hours Hermes runs a health scan of the cluster and, if it finds something it can fix, opens a PR. The PR goes through the same CI as everything else and nothing touches the cluster without going through git. On Mondays it sends an all-clear heartbeat, so silence actually means something.

It’s still evolving, but it’s already more genuinely useful day-to-day than the old chat-window-in-front-of-a-model setup ever was.

Smart home#

  • Home Assistant for home automation, with hamcp (above) exposing it to the AI agent stack
  • eufy-security-ws to bring the Eufy cameras into Home Assistant
  • An ESP32 loft sensor built with ESPHome, keeping an eye on condensation in the loft. Home Assistant sends a Telegram alert when it looks like trouble. The HA config for it lives in the repo as a ConfigMap rather than being clicked together in the UI

Tracking#

  • Fittrackee for exercise/activity tracking, now pulling in new Garmin activities every 3 hours
  • Koinsight for tracking my reading on my hacked Kindle/Koreader App
  • KOReader Sync for syncing reading progress across devices

How it all fits together#

FluxCD#

The whole thing is GitOps. I have a repo with a pretty simple structure:

Each app directory has a kustomization.yaml pointing at its namespace, Helm release, ingress, certs, and storage. Push to the repo and Flux picks it up. There are currently 39 HelmReleases running across the cluster. Flux also manages its own components now, so upgrading Flux is just another PR.

Sealed Secrets#

Since the repo contains secrets (database passwords, API keys, etc), everything is encrypted with Bitnami Sealed Secrets. I create a normal Kubernetes Secret locally, seal it with kubeseal, and commit the encrypted version. Only the controller running in the cluster can decrypt them. It works really well and means I don’t have to worry about what I commit.

Renovate#

Renovate runs as a CronJob inside the cluster itself. It watches Helm chart versions and container image tags (including images in plain Kubernetes manifests now, not just Helm values), then opens PRs when updates are available. Patch and minor bumps on low-risk stuff auto-merge - through Renovate’s own token once every check goes green, since GitHub’s native auto-merge needs branch protection that isn’t available on a private repo under GitHub’s free plan. Everything else I review manually, but it means I’m never more than a PR away from being up to date.

For a while the only check gating that automerge was pre-commit - yamllint, checkov, kube-linter, that kind of static linting. Nothing actually rendered a chart or built an overlay, so a Helm bump that broke its values schema would sail straight through. I added three more CI jobs: kustomize-build renders every changed Kustomize overlay client-side, helm-render resolves each changed HelmRelease’s real chart/version/repo and runs helm template against it (the highest-value check, since that’s the actual failure mode for chart bumps), and cluster-dry-run spins up a throwaway kind cluster on the runner and does a server-side dry-run apply of the whole Flux tree against it, with pinned CRDs installed for every operator the repo uses.

cluster-dry-run looked fine locally but turned up two bugs once it ran for real. CloudNativePG’s CRDs are vendored in the repo, which I’d assumed meant they came along for free, but a CRD and a resource depending on it applied in the same batch doesn’t work reliably since kubectl doesn’t wait for the CRD to register first - the fix was installing it as an earlier step. And kube-prometheus-stack’s Prometheus and Alertmanager CRDs hit an actual API server limit: client-side apply stores the whole submitted manifest in an annotation for future diffing, and those CRDs’ schemas are big enough to blow past the 256KiB annotation cap. Server-side apply doesn’t create that annotation, so switching to it fixed it.

Those checks don’t run on GitHub Actions anymore though. Actions got blocked on billing, so CI now runs on my own Gitea. Gitea keeps a pull mirror of the repo, its Actions runners do the work, and the result gets posted back to the GitHub PR as a status check. Renovate and the automerge flow didn’t have to change at all.

The new-findings-only bit is worth a mention too. Linting now only fails on findings a PR introduces, rather than on every old warning in the repo, which stopped unrelated dependency bumps from going red.

Ingress and TLS#

Traefik comes bundled with K3s so I use that for all the routing, now running two replicas on chilli and lucky. Each app gets its own subdomain and cert-manager handles the TLS certificates. For local dev access I use mkcert.

Databases#

Postgres is handled by CloudNativePG, which lets me run proper Postgres clusters as Kubernetes workloads. Immich, Gitea, Fittrackee, Wallabag, Paperless-ngx, Miniflux, Coder, AFFiNE, Journiv and my CRM all get their own dedicated Postgres instance. Immich’s uses pgvecto.rs for its ML-powered photo search which is pretty neat, and AFFiNE’s has pgvector turned on for its AI features.

Storage#

ZFS on the NAS#

The NAS runs ZFS with the two 12TB drives mirrored, so I get about 12TB usable with redundancy. I’ve split it into datasets so I can apply different policies:

  • nas/media - all the media, lz4 compressed
  • nas/important - the stuff I really can’t lose, with snapshots enabled
  • nas/k8s - where Kubernetes PVCs end up
  • nas/backups - what it says on the tin
  • nas/tmp - scratch space

Snapshots on the important stuff are handled by zfs-auto-snapshot. It’s not a proper backup strategy on its own but it’s saved me more than once. The NFS export only exposes important, k8s and media now, with the root read-only.

How the cluster uses it#

On the Kubernetes side, I use the nfs-subdir-external-provisioner to create a nfs-client StorageClass. Most apps just request a PVC and get a directory on the NAS automatically. There’s a second provisioner just for music storage (Navidrome, Picard, etc need access to the same music library). Deleted PVs get archived rather than wiped, which is a nice safety net when removing apps.

Some apps that need better I/O use local-path storage directly on whichever node they’re scheduled on. One lesson I keep relearning: SQLite on NFS is a bad idea. Apps that use it tend to stall or lock up, so a few of them (like the AFFiNE search indexer) have moved to local-path.

The cluster has 115 PVs at this point. Media-heavy apps like Jellyfin and Immich mount the big ZFS datasets directly. Each database gets 8Gi via CloudNativePG.

Keeping the nodes up to date#

This used to be a lot of manual toil - kernel CVE rollouts node by node, k3s versions drifting apart, little one-off host tweaks I’d forget about. That’s the main reason chilli moved to Fedora CoreOS. The OS is immutable, updates are atomic, and the whole node config lives in git as Butane files with a build script.

A few pieces hold it together:

  • Zincati auto-updates and reboots the FCOS node.
  • A FleetLock server in the cluster makes sure only one node reboots at a time, and drains it first.
  • system-upgrade-controller pins the k3s version on every node, so they can’t drift.
  • A rolling kernel upgrade script for the nodes that aren’t on CoreOS yet.

chilli was the pilot, and if it keeps behaving the plan is to roll it out to the rest. bluey is next. lucky will probably stay on Ubuntu since it’s the ZFS and NFS server, and the Pi might just get retired. The bit I’m most excited about is that the Butane file does the whole setup on first boot, k3s install and cluster join included. So a new node could just be “write the image to a disk, boot it, wait”. I’m also tempted to try network booting the nodes with their Ignition config served from the cluster, so there’s no USB stick involved at all.

The one SELinux gotcha worth writing down: any image whose entrypoint runs as root and chowns /dev/stdout will crashloop on FCOS. The fix is to run it as the image’s own uid.

Unattended reboots brought their own problem. The first time Zincati rebooted chilli, every evicted pod landed on bluey (lucky’s taint keeps most things off it) and stayed there after chilli came back. bluey ran out of memory, IO went through the floor, and CoreDNS, which was single-replica and happened to be on bluey, stopped answering. No DNS means no Flux, no ingress, nothing. Kubernetes never moves pods back once a node returns, which I knew in theory but hadn’t really thought through.

So now CoreDNS runs two replicas and is never placed on bluey, Traefik runs two replicas with a PodDisruptionBudget, and the descheduler runs every 10 minutes to rebalance pods once a node is back. It’s in dry-run for now whilst I make sure it isn’t going to evict anything it shouldn’t.

Node DNS also goes to NextDNS over DoT now, both on the hosts and for pod DNS through CoreDNS.

Monitoring#

I’d gone a bit deep on the monitoring stack at one point, then pulled some of it back out. I dropped Grafana, Loki, and Uptime Kuma - they were extra surface area for dashboards I rarely opened and log queries I rarely ran. Tempo and the OpenTelemetry Collector went too, since nothing was actually sending them traces. Prometheus and Alertmanager stayed, untouched.

The core is kube-prometheus-stack which gives me Prometheus and Alertmanager.

For alerting, Alertmanager sends critical alerts to ntfy, which pushes notifications to my phone. I’ve set up inhibition rules so I don’t get spammed - critical alerts suppress warnings, warnings suppress info-level stuff. Telegram is a second delivery channel, mainly so a single notification path being down can’t silently mean I miss something critical.

I’ve added a few alerts after finding gaps the hard way: stale CloudNativePG backups and failing WAL archiving, VolSync metrics going missing altogether, and Prometheus’s own head block not compacting.

Off-site backups are handled by Volsync, which replicates PVCs to Cloudflare R2. It now covers the important documents on the NAS too, not just the cluster’s PVCs, which let me retire a couple of older backup cron jobs. CloudNativePG databases get their own continuous backups to R2 as well. The Sealed Secrets controller key is also backed up to R2 monthly so I can recover the cluster from scratch if needed.

Lessons learned#

The stuff that broke, and what I changed so it doesn’t again.

Cooling, it turns out, matters#

For a while I had a load of “random” problems across the cluster - controllers restarting, API timeouts, nodes getting tainted unreachable. The actual cause was chilli cooking itself. It was hitting 95-96C with the fan maxed out, and the kernel was injecting idle time to cool it down. On top of that, the k3s datastore (a SQLite file) lived on a 5400rpm laptop HDD. A slow, throttled API server makes every controller in the cluster lose its leader lease and restart.

The fix was a mix of hardware and scheduling. chilli got a re-paste and an SSD, and I moved every stateless controller I could over to lucky. That took it from 101C and a load of 10 down to 69C and a load of 1.5. All in all, a pretty nice result for a tube of thermal paste.

Boot order bugs#

A power outage exposed a boot-order bug worth noting: on one node, containerd’s data directory lives on a drive mounted via /etc/fstab with nofail. Nothing told k3s-agent to actually wait for that mount before starting, so a reboot could race containerd against the drive and corrupt its local image cache - which is exactly what happened. Fixed with a systemd drop-in adding RequiresMountsFor= for the mount path. lucky got the same treatment so k3s-agent waits for zfs-mount.

Another one on lucky: a pod there mounted NFS from the NAS it was running on. That loopback NFS mount wedged nfsd, which took down NFS for the whole cluster. All loopback NFS on lucky is gone now. Anything scheduled there either has no NFS volumes or uses hostPath directly.

The R2 bill that kept growing#

My R2 storage bill started climbing for no obvious reason. Turned out spec.paused: true on a VolSync ReplicationSource doesn’t just pause the schedule the way the name implies - it also forces the generated backup Job’s parallelism to 0, so it silently creates zero pods, forever, with no error surfaced anywhere. Compounding that, a stale restic lock left over from a manual size-check I’d never cleaned up had been quietly blocking one app’s backups for 18 days.

Worse: the Prometheus alert that was supposed to catch exactly this kind of backup failure had never actually worked. It watched kube_pod_status_phase for failed pods, but VolSync garbage-collects those pods almost instantly, so the alert could structurally never fire. Fixed it by alerting on VolSync’s own volsync_volume_out_of_sync metric instead (had to add a missing ServiceMonitor just to get it scraped in the first place), and added a weekly job that diffs the live R2 bucket against known backup sources - so orphaned data, like the ~5GB the Matrix decommission left behind, gets caught automatically instead of by accident.

Stale restic locks have come back a few times since, on Immich and CryptPad. The fix that sticks is committing the unlock to the repo and letting Flux apply it. Patching it live just loses the race with Flux.

What’s next#

Honestly this changes all the time but the things on my mind:

  • Moving bluey onto Fedora CoreOS too, and finding a replacement for muffin
  • Taking the descheduler out of dry-run once I trust it
  • Finishing the CryptPad export so I can remove it
  • Proper network segmentation. Right now everything’s flat on the same LAN which isn’t great
